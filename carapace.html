What is Carapace

Carapace is a confined HTML/CSS/JS renderer for security researchers, written in Rust. Point it at a hostile URL and it loads the page in headless Chromium with JavaScript enabled — so runtime-injected attacks (ClickFix, SocGholish, ClearFake, wallet drainers) actually render and become visible in the screenshot, rather than showing the blank page a JS-disabled scanner sees.

Because it executes attacker code, the browser is treated as hostile: every connection it makes goes through an SSRF-enforcing policy proxy. The page's own same-origin content and a vetted CDN/font list are fetched live, so the page renders as a visitor would see it; every cross-origin request — the C2 and exfiltration signal — is refused and recorded as evidence. A threat report is produced alongside every render.

A /solve endpoint gets past Cloudflare challenges and JavaScript cloaking gates and returns the page the server actually served, with the navigation chain the browser was sent down.

Open-source (MIT): source, issues, and releases live at github.com/DanDreadless/Carapace. Carapace is standalone, but also drops in as the renderer for Insight — see Works With Insight.

How It Works

Every render runs the same pipeline:

  1. Fetch — a hardened Rust HTTP client (reqwest, HTTP/2) fetches the URL with SSRF protection and decompression-bomb limits.
  2. Parse & sanitise — the HTML is parsed and scrubbed: <script> tags, event handlers, javascript: URIs, and data: URLs are stripped, recording an HTML flag for each removal.
  3. Static JS analysis — all collected script content is walked with an AST analyser (OXC) before removal — detecting eval, obfuscation, exfiltration calls, DOM sinks, clipboard hijacks, and sandbox-evasion probes.
  4. JS sandbox — for framework-driven pages (React, Vue, Angular…), scripts run in an isolated rquickjs runtime; network APIs are shimmed to log and block all outbound calls.
  5. Inline resources — external stylesheets and images are fetched and inlined as data URIs (bounded in size); external url() references in CSS are blocked. This produces the self-contained page used by the offline fallback.
  6. Render (live) — Chromium navigates the real URL with JavaScript enabled, driven over the Chrome DevTools Protocol through a pipe (--remote-debugging-pipe — no debug port a page could reach) when CARAPACE_CDP is on, otherwise via Chromium's CLI. All traffic goes through the policy proxy. A Windows identity is presented so OS-gated payloads execute, navigation is suppressed so the attack UI stays on screen, and the page settles on network-idle — floored, so a delayed overlay still injects — before the screenshot and post-JS DOM are captured.
  7. Navigation capture — main-frame navigations are intercepted with CDP Fetch (Document requests only): the first is the validated page load and continues; every later one is a client-side redirect whose JS-computed destination is recorded and blocked, never dispatched. Destinations come back as nav_targets for the caller to SSRF-validate and scan.
  8. Offline fallback — if the live render fails or comes back blank, the self-contained sanitised page from step 5 is rendered with a proxy that refuses every connection and a fetch/XMLHttpRequest mock, so data-driven pages still show something.
  9. Threat report — findings from static analysis, the JS sandbox, the CSS overlay detector, the post-render DOM diff, and the network intercept log are collected into a JSON report.
  10. Annotation — a verdict badge is composited onto every screenshot showing the domain, risk score, verdict label, and scan timestamp.

Security Model

Carapace executes attacker JavaScript. The browser is therefore treated as hostile and the container is the trust boundary — not the sanitiser.

  • Policy proxy — every Chromium connection goes through it. Same-origin (the page's own host and subdomains) and a vetted read-only CDN/font list are forwarded; everything else is refused with a 503 and recorded as INTERCEPTED_REQUEST. The proxy resolves each host itself and rejects the connection if any resolved IP is private, loopback, link-local, metadata or CGNAT — which also defeats DNS rebinding. Forwarded connections are bounded in count, time and bytes.
  • Control channel — CDP runs over --remote-debugging-pipe, never a TCP port, so the page cannot reach it. Event domains an adversarial page could flood are kept off, or drained with bounded queues.
  • Hard deadlines — each browser runs in its own process group with a watchdog that killpgs it at the deadline. A hung or hostile page cannot outlive its budget.
  • Memory bounds — one renderer process per page, a capped V8 heap, and oom_score_adj=1000 so a runaway page loses its own browser rather than taking down the server.
  • Isolation between renders — a fresh browser process and a private profile per render.
  • --disable-blink-features=AutomationControlled suppresses the navigator.webdriver flag, so evasive scripts execute their real attack path rather than a clean scanner path.
  • --run-all-compositor-stages-before-draw ensures layout, paint, and compositing complete before the PNG is captured, preventing partial blank renders.
  • SSRF protection blocks private, loopback, and link-local ranges at both URL-validation and DNS-resolution time.
  • The rquickjs sandbox shims fetch, XMLHttpRequest, and WebSocket — every network call is logged and blocked.
  • Docker — runs as a non-root user (uid 1000) with all Linux capabilities dropped. In production also run it --read-only (tmpfs for /tmp, /home/carapace, /output), with --init to reap Chromium's children, bounded memory / CPU / PIDs, and on a network that can reach nothing but the internet. Insight runs it inside a VPN namespace attached to a render-only network, with a host egress firewall dropping private ranges.

Offline path only. On the offline fallback the live page is never loaded, so that path additionally blocks remote fonts (--disable-remote-fonts), strips CSS @import, external url() and @font-face, removes every on* attribute, <script>, <iframe>, <object>, <embed> and <form> before handing the page to Chromium, and gives JS timers up to 5 seconds of virtual time (--virtual-time-budget=5000) so delayed overlays still fire. The wkhtmltoimage fallback of last resort runs with --disable-javascript.

Quick Start

Docker (recommended)

Build once:

docker build -t carapace:latest .

Render a URL to PNG:

docker run --rm --cap-drop=ALL --security-opt no-new-privileges:true \
  -v "/tmp:/output" carapace:latest render https://example.com -o /output/render.png

Threat report only (no image):

docker run --rm --cap-drop=ALL --security-opt no-new-privileges:true \
  -v "/tmp:/output" carapace:latest render https://example.com --output-format json -o /output/report.json

Start the HTTP API server:

docker run --rm --cap-drop=ALL --security-opt no-new-privileges:true \
  -e CARAPACE_API_KEY=s3cr3t -p 8080:8080 carapace:latest serve --port 8080

Native (development)

cargo build --release
./target/release/carapace render https://example.com -o output.png
./target/release/carapace render https://example.com --output-format json -o report.json
./target/release/carapace serve --port 8080

POST /analyse

Runs OXC static JS analysis on a URL or raw content without Chromium. Use this for direct .js script URLs — feeding raw JS to /render hangs Chromium because async JS never resolves in a blank-page context.

curl -s -X POST http://localhost:8080/analyse \
  -H "Content-Type: application/json" -H "X-API-Key: s3cr3t" \
  -d '{"url":"https://example.com/app.js"}' | jq .threat_report

Request body — either url or content must be provided (content wins if both are given):

{ "url": "https://example.com/app.js", "content": null, "max_size": null, "source_name": null }

For files larger than 512 KB, analysis runs on overlapping 256 KB chunks (32 KB overlap) to catch patterns split at a boundary. The response has the same shape as /render with output: null; only threat_report is populated.

Getting Past Gates (POST /solve)

Some pages show a scanner nothing until a real browser has passed a gate. /solve loads the URL in the confined browser, lets whatever stands in front of the content play out, and returns the document the server actually served plus the path the browser was sent down. Two uses:

  • Cloudflare bot challenges that a plain or TLS-impersonating client cannot pass. The policy proxy additionally allows challenges.cloudflare.com (Turnstile); the User-Agent is Chromium's own with the HeadlessChrome token removed, set by flag so the Sec-CH-UA client hints stay native and consistent.
  • JavaScript cloaking gates — a content-less page that re-requests itself with a proof-of-JS token, after which the server picks what to serve. No render bootstrap is injected, so the gate's own navigation fires. If the gate forwards off-site (a TDS doorway) the cross-origin hop is recorded in nav_chain but never fetched — the policy proxy still refuses it.
curl -s -X POST http://localhost:8080/solve \
  -H "Content-Type: application/json" -H "X-API-Key: s3cr3t" \
  -d '{"url":"https://example.com/"}'

Request: {"url": "https://..."} — http(s) only (https-only when the server enforces it), a hostname rather than an IP literal, and no credentials in the URL.

Response:

{
  "solved": true,
  "challenge_absent": false,
  "clearance_source": "fresh",
  "final_url": "https://example.com/",
  "title": "Example",
  "cookie_names": ["cf_clearance"],
  "user_agent": "Mozilla/5.0 (X11; Linux x86_64) ... Chrome/151.0.0.0 Safari/537.36",
  "document": {
    "url": "https://example.com/",
    "status": 200,
    "headers": { "content-type": "text/html; charset=utf-8", "server": "cloudflare" },
    "body_b64": "<base64 raw response body>",
    "truncated": false
  },
  "nav_chain": ["https://example.com/", "https://example.com/?__cf_chl_tk=..."],
  "elapsed_ms": 3162,
  "intercepted": []
}
  • solved — cf_clearance was issued and the "Just a moment…" interstitial is gone. challenge_absent — the page loaded with no challenge at all (or a JS gate was followed). An interactive Turnstile that cannot be passed returns both false, never an error.
  • document — the last main-frame response the browser received (sub-frames such as the Turnstile iframe are ignored), captured over CDP Network: raw body (base64, capped at 5 MB) plus headers. null if it could not be captured, and never returned for an uncleared interstitial.
  • nav_chain — ordered main-frame navigations (≤ 10, http/https), server redirects included.
  • clearance_source — fresh, cached, or none. Clearance cookies are cached per host inside Carapace (≤ 25 min) and fed back into the next solve's browser before it navigates, so a repeat request skips the challenge. Clearance values never leave Carapace — only cookie_names are returned. Returning the page rather than the cookies also matters when the caller's egress IP differs from Carapace's: clearance is bound to the IP that solved it.
Treat the response as untrusted input. Every field was produced by a browser that has just run the target's JavaScript. A solve holds a render slot and is capped at 25 seconds, and always uses CDP regardless of how the CDP environment flags are set.

Threat Report

Every render produces a threat report. From the CLI it is written to <output>.threat.json; via the API it is returned inline as threat_report.

{
  "url": "https://example.com",
  "timestamp": "2026-04-18T09:00:00Z",
  "framework_detected": "Unknown",
  "tech_stack": [],
  "risk_score": 0,
  "render_skipped": false,
  "render_blank": false,
  "blank_ratio": 0.0,
  "render_mode": "live",
  "rendered_html": "",
  "normalized_scripts": [],
  "decoded_payloads": [],
  "runtime_scripts": [],
  "nav_targets": [],
  "html_flags": [],
  "js_flags": [],
  "blocked_network": [],
  "flags": []
}
  • risk_score — 0–100. Static JS analysis, HTML sanitisation, CSS overlay detection, post-render DOM diff, runtime network interception, drive-by detection, QR-code (quishing) decoding, and Browser-in-the-Browser detection all contribute. Base score is one weight per unique code (Critical 40, High 20, Medium 10, Low 5); a repeated code adds 2 points per extra occurrence, capped at 10 per code; the total is capped at 100.
  • flags — the deduplicated primary findings list. html_flags / js_flags are the raw per-occurrence lists behind the volume bonus; blocked_network lists every URL JavaScript tried to reach at runtime and had refused.
  • render_mode — which strategy produced the delivered screenshot: "live" (navigated the real URL through the policy proxy), "offline_fallback" (live render failed or came back blank), or "offline" (live disabled). render_blank / blank_ratio flag a screenshot that came back effectively all-white after the retry ladder was exhausted.
  • rendered_html — the post-JS DOM of a successful live render (capped for transport), so a caller can re-run its own analysers on what the browser actually rendered. Essential for service-worker-gated content (IPFS dweb.link) and fully JS-rendered SPAs.
  • normalized_scripts (Tier-0 deobfuscation: constants folded) and decoded_payloads (Tier-2: cleartext captured from eval / Function / document.write sinks while the script's own decoder ran) expose the resolved payload behind obfuscation.
  • nav_targets — main-frame redirect destinations captured and blocked, never dispatched, on a live render; includes JS-computed interstitial and TDS destinations no static analysis can resolve (≤ 10; needs CARAPACE_CDP_NAV_CAPTURE). The caller SSRF-validates them before following.
  • runtime_scripts — bodies of scripts loaded at runtime via fetch()+eval or dynamic import() that never appear as <script> tags (needs CARAPACE_CDP_CAPTURE).
  • render_skipped — true when the content-type was not text/html: the HTML/render pipeline is bypassed and OXC analysis runs on the raw body (e.g. a .js URL submitted to /analyse).

Sandbox evasion (headless-detection probes)

These probes are split on whether the result actually gates content delivery — a redirect, DOM rewrite, script injection or fetch nearby. Gated is the cloaking case and stays HIGH. Ungated is ordinary anti-fraud SDK, analytics and framework behaviour, so it drops to LOW and carries no verdict on its own. HeadlessChrome and friends are the exception: they name automation tooling, which is a tight enough signal to stay HIGH without a gate.

Tech Detection

Carapace fingerprints the technology stack from the pre-sanitisation DOM — before custom elements and framework attributes are stripped — and records it under tech_stack. Coverage includes React, Vue, Angular, Svelte, Next.js, Nuxt, HTMX, Alpine.js, Livewire, Tailwind CSS, Bootstrap, Bulma, shadcn/ui, WordPress, Drupal, Joomla, Shopify, Magento, Wix, Squarespace, jQuery, Lodash, Moment.js, Axios, Socket.io, and more.

Renderer Fallback

The render ladder, in order:

  1. Live render — the real URL, JavaScript enabled, through the policy proxy. Over CDP when CARAPACE_CDP is on, with the CLI live render as its own fallback.
  2. Offline render — the sanitised self-contained page, JavaScript still enabled, every connection refused and the network APIs mocked. Used when the live render fails or comes back blank.
  3. wkhtmltoimage — only if Chromium is unavailable at all, with JavaScript disabled.

render_mode in the threat report records which one produced the delivered screenshot, and render_blank / blank_ratio record whether it still came back effectively all-white. Pass --no-browser to force the built-in Rust renderer (tiny-skia + taffy layout) — approximate, supporting the basic box model, flexbox, and inline text only; use it when no headless browser is available.

Works With Insight

Carapace runs standalone, but it is also the renderer behind Insight. Deploy it as a sidecar and point Insight at it with CARAPACE_URL (and optionally CARAPACE_API_KEY). Every Insight scan then calls /render, embeds the screenshot, and converts Carapace's threat flags into Insight findings under the Renderer category — remapping a few severities to suit a whole-scan verdict rather than a single render, and aggregating the routine sanitiser codes into one informational finding.

Insight also uses /solve for gate handling: a Cloudflare challenge that survives TLS-fingerprint impersonation, and JavaScript cloaking gates whose off-site forwards identify a TDS doorway. The document /solve returns becomes the page Insight analyses, and the nav_chain becomes the evidence. Insight runs the container inside a VPN namespace on a render-only network, so the renderer cannot reach its database or cache and never visits a target from the host's own IP.

If Carapace is unavailable the Insight scan continues without it — the renderer phase is best-effort, never a hard dependency. See the Insight documentation for the integration details.
